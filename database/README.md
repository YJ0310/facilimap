# T05 / T06 — SQLite schema and indexes

Based on the five tables and proposed fields in T08 (PR #2), and T07 category
labels (PR #1). The team leader confirmed that users must log in before reporting.
This change adds SQL only and does not change the Node.js/Express framework.

## Initialize a new database

Install the SQLite command-line tool and, from the repository root, run:

```sh
sqlite3 database/facilimap.db
```

At the SQLite prompt:

```sql
.bail on
.read database/schema.sql
.read database/indexes.sql
PRAGMA foreign_key_check;
PRAGMA integrity_check;
.quit
```

Expected checks: no foreign-key rows, and `ok` for integrity. If initialization
fails, stop and inspect the error. Do not run this bootstrap against an existing
application database: it deliberately fails when tables already exist instead
of silently treating an outdated schema as current. `indexes.sql` is repeatable.
Schema changes to an existing populated database require a separate migration.
No database binary, real accounts, credentials, photos or seed facilities are
included. T13 can populate the confirmed T07 categories and surveyed facilities.

## Physical model

The SQL files are authoritative for column types, keys and nullability. Names
match T08. All five tables are retained without introducing extra entities.

- `USER.user_id`: nonempty TEXT key, allowing a stable identity from the future
  login implementation. Proposed roles are `user` and `admin`. No password or
  login provider is assumed; authentication implementation is a separate task.
- Other primary keys: INTEGER keys generated by SQLite when omitted. No extra
  AUTOINCREMENT bookkeeping is required.
- `FACILITY.category_id`: required. `ISSUE_REPORT.reporter_user_id`: required.
  `ISSUE_REPORT.facility_id`: optional, following T08.
- Both report and facility coordinates are required, numeric and range checked.
  This preserves a report's submitted location independently of its facility.
- `building`, `floor`, `opening_hours`, `last_verified_at` and `photo_ref` are
  optional. Floor and hours use TEXT to accommodate values such as `G` and
  human-readable opening schedules. A photo reference is a path/key, not binary.
- Report creation and review timestamps default to UTC ISO 8601 strings.
  Application-supplied timestamps must use the same format. A null verification
  timestamp means the facility has not yet been verified.
- Each review has one report and one reviewing user. `report_id` is deliberately
  not UNIQUE in the log: a report can have zero or many reviews.

## T06 integrity and query support

Every database connection MUST execute `PRAGMA foreign_keys = ON` before opening
transactions and verify that the result is `1`. The schema script setting does
not persist to future API connections. Configure this in the chosen Node SQLite
driver when the backend connection is implemented.

All references use `ON DELETE RESTRICT ON UPDATE RESTRICT`. This proposed policy
prevents deleting linked users, categories, facilities or reports and avoids
cascading away report/review history. It is not an immutable audit-log mechanism;
authorization for direct record deletion remains an application responsibility.

Six indexes cover facility category filtering, a user's report history, reports
for a facility, reports by status/time, a report's review history, and reviews by
administrator. Composite indexes also cover their leading foreign-key column;
there are no duplicate single-column indexes for these keys. Primary-key and
UNIQUE indexes are already created by SQLite.

## Review decisions still open

1. **Status vocabulary and transitions:** no approved facility/report status list
   was found. Status fields therefore require nonempty TEXT with no default or
   fixed enum. This is intentionally provisional, not a final workflow. Confirm
   the values with the team, then add matching validation/constraints before
   implementing production report/review endpoints. Test statuses are fixtures
   only and must not be used as seed data.
2. **Roles and deletion:** `user`/`admin` role labels and RESTRICT deletion are
   proposed implementation choices for team review, not confirmed business rules.
3. **API enforcement:** a foreign key proves that a user exists, not that the
   caller logged in. The API must authenticate requests and derive the reporter
   identity from the session, rather than trusting a submitted user ID. It must
   also verify the reviewer's admin role. The log foreign key alone does NOT
   enforce that role. Change the report status and insert its review event in
   the same transaction, validating the previous status, to prevent divergence.

## Tests

From the repository root, using Node.js 22.13+ (or Node.js 24):

```sh
node --test database/test/schema.test.cjs
```

Tests use Node's built-in SQLite module and an in-memory database; no npm package,
Python backend or on-disk database is needed. Older Node 22 releases may require
an experimental SQLite flag; upgrade to the version above for this command.
Tests cover the five tables, six indexes, required reporter, all foreign-key
relationships, optional facility link, multiple reviews, restricted parent
changes, invalid coordinates/content, uniqueness, roles, and integrity checks.
